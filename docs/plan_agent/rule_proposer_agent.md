# Rule Proposer Agent Node — Implementation Plan

## Context

The Profiler Agent is done. [profiler_node.py](src/agents/nodes/profiler_node.py) produces `dataset_profile_digest` — a compact per-table/per-column summary generated by [generate_profile_digest()](src/agents/tools/profile_digest.py#L3). Sample output: `data/results/debug_profile_digest_20260806_124531.json` (~9 Olist tables, wrapped under a `dataset_profile_digest` top-level key).

Step 2 of the v2 agent flow ([architecture_diagram.md:151](docs/architecture_diagram.md#L151)) is the **LLM Rule Proposer** → **HITL** → Test Generator. Right now [rule_proposer_node.py](src/agents/nodes/rule_proposer_node.py) is an empty file.

Three problems this plan solves:

1. **Context blowup.** Feeding the whole digest (all tables) into one LLM call is wasteful, degrades rule quality, and will eventually exceed the window. → Split the digest per table; one LLM call per table.
2. **Latency.** 9–10 sequential LLM calls is slow. → Fan out with `asyncio.gather` + a concurrency semaphore, mirroring how `raw_profiler_node` already uses `asyncio.to_thread`.
3. **Unstructured output.** Free-text rules can't be rendered in the Rule Review table or diffed after a Steward edit. → `llm.with_structured_output(...)` against a closed Pydantic schema, so every rule arrives as a typed row ready for HITL and, later, for the dbt generator.

**Decisions already made** (from clarifying questions): DB-backed HITL with the graph split into two runs (no LangGraph `interrupt()`/checkpointer); split in-memory with optional debug-file dump; ChromaDB RAG stubbed for now; per-table retry with failure isolation.

## Part A — Structured output schema

### New file: `src/models/rule_schemas.py`

Pydantic v2 models. **Critical detail:** do *not* type rule parameters as a bare `dict`. `with_structured_output` compiles the model to a JSON Schema, and an open `dict` becomes `additionalProperties: true`, which Mistral/OpenAI strict function-calling either rejects or fills unpredictably. Use a closed model with all-optional typed fields instead.

```python
class RuleType(str, Enum):
    NOT_NULL = "NOT_NULL"
    UNIQUE = "UNIQUE"
    RANGE = "RANGE"
    ACCEPTED_VALUES = "ACCEPTED_VALUES"  # enum check
    REGEX_FORMAT = "REGEX_FORMAT"
    FRESHNESS = "FRESHNESS"
    ROW_COUNT = "ROW_COUNT"  # table-level
    NULL_RATE = "NULL_RATE"  # null_pct must stay below a ceiling


class Severity(str, Enum):
    CRITICAL = "CRITICAL"
    HIGH = "HIGH"
    MEDIUM = "MEDIUM"
    LOW = "LOW"


class RuleParameters(BaseModel):
    """Closed param bag — every field optional, only the ones relevant to rule_type are filled."""

    min: float | None = None
    max: float | None = None
    accepted_values: list[str] | None = None
    regex: str | None = None
    max_age_hours: float | None = None
    max_null_pct: float | None = None
    min_row_count: int | None = None


class ProposedRule(BaseModel):
    column: str | None = Field(None, description="None cho rule cấp bảng (ROW_COUNT)")
    rule_type: RuleType
    parameters: RuleParameters = Field(default_factory=RuleParameters)
    confidence_score: float = Field(..., ge=0.0, le=1.0)
    severity: Severity
    ai_reason: str = Field(..., description="Lý do đề xuất, bằng tiếng Việt, dẫn chiếu số liệu profile cụ thể")


class TableRuleProposal(BaseModel):
    """Schema the LLM is bound to — one call per table."""

    table: str
    rules: list[ProposedRule]
```

**`rule_id` is assigned in Python, not by the LLM** — models are unreliable at generating unique/sequential IDs across parallel calls. After each call returns, stamp `f"{table}.{column or '_table'}.{rule_type}"` (or a running counter) in the node.

**Validation guardrails to add** as a `@model_validator` on `ProposedRule`: `RANGE` requires `min` or `max`; `ACCEPTED_VALUES` requires a non-empty list; `REGEX_FORMAT` requires `regex`. A rule failing this is dropped with a warning rather than sent to a Steward as a half-formed row.

## Part C — The prompt

### Modify: `src/agents/nodes/templates.py`

Add `rule_proposer_prompt` as a `ChatPromptTemplate`, matching the existing `profiler_node_prompt` style (Vietnamese system prompt, JSON fenced in the user turn). Input variables: `table_name`, `table_digest`, `domain_context`, `historical_rules`.

System prompt must cover:
- Role: DQ expert for a ride-hailing domain.
- The 8 `RuleType` values and when each applies — tie them to the `role` and `signals` fields the digest already emits: `signals: ["no_nulls"]` → `NOT_NULL`; `["unique_in_sample"]` + `role: "id"` → `UNIQUE`; `role: "categorical"` + `values` → `ACCEPTED_VALUES`; `role: "numeric"` + `range` → `RANGE`; `role: "datetime"` → `FRESHNESS`.
- **Sampling caveat:** when `sample.rate < 1.0`, the digest carries `sample.caveat`. Instruct the model to *lower confidence* and *widen ranges* in that case rather than proposing tight thresholds off a sample.
- Do not invent columns; only propose against names present in the input.
- `ai_reason` must cite an actual number from the digest (e.g. "null_pct = 0.0 trên 99,441 dòng").
- Ranges should be padded beyond the observed min/max (a `RANGE` pinned exactly to observed values will fire on the first legitimate new record).

**Set `temperature` low (0.0–0.2) for this node.** The global default is `0.7` ([config.py:30](src/config.py#L30)), which is wrong for schema-constrained rule generation.

### Implement: `src/agents/nodes/rule_proposer_node.py`

Follows the conventions already in [profiler_node.py](src/agents/nodes/profiler_node.py): module-level `logger`, `async def <name>_node(state: AgentState) -> dict` returning only the keys it writes, and a `main()` debug harness under `if __name__ == "__main__"` that dumps to `data/results/`.

```
async def _propose_for_table(table_name, table_digest, structured_llm, semaphore, max_retries) -> TableRuleProposal
    async with semaphore:
        for attempt in range(max_retries + 1):
            try:
                historical = query_historical_rules(table_name, [c["name"] for c in ...])
                messages = rule_proposer_prompt.format_messages(
                    table_name=..., table_digest=json.dumps(table_digest, ensure_ascii=False),
                    domain_context=DOMAIN_CONTEXT, historical_rules=json.dumps(historical, ...))
                return await structured_llm.ainvoke(messages)
            except (ValidationError, Exception) as e:
                log + exponential backoff (1s, 2s, 4s); re-raise on final attempt

async def rule_proposer_node(state: AgentState) -> dict
    1. per_table = split_digest_by_table(state["dataset_profile_digest"])
    2. if debug flag: dump_table_digests(per_table, "data/results/digest_by_table")
    3. llm = get_llm(settings.llm_provider, temperature=0.1)
       structured_llm = llm.with_structured_output(TableRuleProposal)
    4. sem = asyncio.Semaphore(settings.rule_proposer_concurrency)   # default 10
       results = await asyncio.gather(*(_propose_for_table(...) for t in per_table),
                                      return_exceptions=True)
    5. Walk results: successes → validate + stamp rule_id + flatten to list[dict];
       exceptions → append {"table": t, "error": str(e)} to errors.
    6. return {"proposed_rules": flat_rules,
               "rule_proposal_errors": errors,
               "rule_run_id": run_id}
```

`return_exceptions=True` is what delivers the "one bad table doesn't kill the run" requirement — pair it with zipping results back against the table-name list so a failure can be attributed.

`run_id`: generate a `uuid4().hex` (or timestamp slug) in the node so every rule row from one fan-out shares a batch key. This is what the Rule Review Screen filters on.

## Part E — HITL (DB-backed, graph split into two runs)

This is the piece that was hard to picture. Concretely, there is **no pause inside the graph**. Run 1 ends after persisting rules as `PENDING`; the human acts through normal REST; Run 2 is started later by a separate endpoint.

```
Run 1 (POST /dq/propose)
  raw_profiler -> profiler_digest -> rule_proposer (async x N tables) -> persist_rules(PENDING) -> END
                                                                              |
                                                        [ Screen 5: Rule Review Table ]
                                                        GET  /dq/rules?run_id=...&status=PENDING
                                                        PATCH /dq/rules/{id}         (approve/reject/edit one)
                                                        POST /dq/rules/bulk-review   (checkbox multi-approve)
                                                                              |
Run 2 (POST /dq/runs/{run_id}/generate-tests)
  load APPROVED rules from DB -> test_generator -> test_runner -> anomaly -> END
```

Why this over LangGraph `interrupt()`: no checkpointer dependency, state survives an API restart, the Steward can walk away for a day, and the Rule Review Screen described at [Wireframe_UI_Flow.md:83](docs/G1/Wireframe_UI_Flow.md#L83) gets a plain queryable table instead of a serialized graph snapshot.
